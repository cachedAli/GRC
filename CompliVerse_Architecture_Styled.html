FastAPI Middleware Pipeline Per-Tenant Routing

API Client (Axios HTTP Interceptor)

Single HTTP client used by every page. Injects Authorization: Bearer <jwt> and X-Tenant-Slug from local storage on every outbound call.

grc-frontend/src/lib/api.ts

CORS Policy Middleware

First middleware in the FastAPI pipeline. Configured permissively for development; production tightens to the tenant-domain allow-list.

backend/grc/main.py

Tenant Resolution Middleware

Resolves the request's tenant from X-Tenant-Slug or subdomain, loads the schema_name, attaches it to request.state.

backend/grc/middleware/subdomain.py

Audit Logging Middleware

Intercepts every inbound HTTP request. Captures actor, route, status and payload metadata and persists a grc_audit_logs record.

backend/grc/main.py · backend/grc/audit_logger.py

JWT Authentication Dependency

FastAPI Depends(get_current_user) decodes and verifies the bearer token signature and expiry, then loads the corresponding user record.

backend/grc/routers/auth_router.py

Role-Based Access Control (RBAC)

Per-route require_permission("module:submodule:action") dependency, checked against the tenant-scoped role_permissions table.

backend/grc/permissions.py

Tenant Session Helper

Per-request SQLAlchemy session that issues SET search_path TO "tenant_<slug>", public before any query, ensuring tenant isolation.

backend/grc/tenant_manager.py

Per-Tenant PostgreSQL Schemas (tenant_<slug>)

One PostgreSQL schema per tenant, pinned per request via search_path. Holds the data that must never leak across tenants.

usersrolespermissions role_permissionsuser_roles organization_profileaudit_logs

File / Object Storage

Binary evidence and framework PDFs stored on the local filesystem under backend/uploads/; the row in grc_documents holds metadata and the on-disk path.

Audit Log Streams

Two complementary append-only streams HTTP audit (captured by middleware) and business audit (captured by services). Both are queryable from the audit dashboard.

Cache / Vector Store (Reserved)

Not currently in use. Search is SQL-driven and AI calls are stateless. A pgvector store is planned next for retrieval-augmented evidence search.

About this Diagram

About this Diagram

This diagram describes the CompliVerse AI platform as currently implemented. Every component card cites the real router, module, middleware or third-party service it represents in the codebase, with the source path included so engineering reviewers can trace the diagram back to the implementation.

The seven layers are laid out top-to-bottom in the order a typical request traverses the system: a request enters at the Frontend, is authenticated and tenant-scoped at the API Gateway, executes Business Logic, optionally invokes the AI / Automation tier, triggers Backend Services, reads or writes the Data tier, and where applicable reaches out to External Systems.

Manual approval steps are highlighted as Human-in-the-Loop Approval Gates — these are the points at which automated processing explicitly hands off to a person before the workflow advances. They are visually distinct (hatched amber background, dashed border, ribbon header) so reviewers can immediately spot every place where a human decision is required.
